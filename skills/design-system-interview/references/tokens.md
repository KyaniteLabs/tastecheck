# Design Tokens — The Canonical Contract (all skills use exactly these names)

Read when writing the artifact. The interview's decisions become **design tokens** the
other frontend skills consume. Keep the structure simple and current (2026 consensus):
**two tiers — primitive → semantic** — and only add a third (component) tier if truly
needed. Starting with primitive + semantic is the recommended default; component-scoped
tokens are a "only when necessary" escalation.

> **This file is the glossary of record.** Every tastecheck skill (theming,
> color-system, web-typography, component-states, data-viz, micro-motion,
> spacing-system, …) reads and writes **these exact token names**. If a skill needs a
> token this file doesn't define, extend this contract — never invent a parallel name.

## The two tiers (start here)

1. **Primitive (raw) tokens** — the actual values, named by what they *are*. No meaning,
   just the palette/scale. E.g. `--brand-600: oklch(0.54 0.16 30)`, `--space-4: 1rem`,
   `--step-2: clamp(…)`. Generated, not hand-picked (color-system builds the ramp,
   web-typography the scale, spacing-system the spacing).
2. **Semantic (role) tokens** — named by *job*, referencing primitives. This is what
   components use. E.g. `--color-bg`, `--color-text`, `--color-primary`,
   `--radius-control`. Re-theming = remap these.

Components reference **semantic only**, never primitives. That's what makes the system
coherent and themeable (and what lets `theming` swap the mapping for dark and high contrast).

Optional third tier — **component tokens** (`--btn-bg`) — only when a component needs
to diverge from the semantic defaults. Don't add it preemptively; it's overhead.

## The canonical glossary

### Color — semantic (components use these; `theming` remaps them per theme)

| Token | Role |
|---|---|
| `--color-bg` | page ground |
| `--color-surface-1` / `--color-surface-2` (/ `-3` if a dark elevation ramp needs it) | raised surfaces (each step *lighter* in dark mode) |
| `--color-text` / `--color-text-muted` | ink / secondary ink |
| `--color-border` | hairlines, dividers, input borders |
| `--color-primary` / `--color-primary-hover` / `--color-primary-ink` | primary action bg, its hover, text *on* it |
| `--color-accent` / `--color-accent-ink` | the sharp accent, text *on* it |
| `--color-focus` | the focus ring |
| `--color-success` / `--color-error` / `--color-warning` / `--color-info` | semantic states |

### Color — primitive (generated by `color-system`)
`--brand-50…--brand-900`, `--neutral-50…--neutral-950`, `--accent-300…--accent-700`
(OKLCH, constant hue, stepped L, chroma tapering at the extremes).

### Type (faces from the interview; scale generated by `web-typography`)
`--font-display`, `--font-body`, `--font-mono` · `--step--1…--step-5` (fluid scale) ·
`--measure` (line-length cap, e.g. `66ch`).

### Space (scale generated by `spacing-system`)
`--space-1…--space-9` (one geometric scale) · `--space-section: clamp(48px, 32px + 4vw, 96px)` (vertical rhythm
between page sections).

### Shape & elevation
`--radius-control`, `--radius-card`, `--radius-pill` (pill reserved for tags/chips/
avatars — never text CTAs; see `deslop-ui`) · `--shadow-card`, `--shadow-float`.

### Motion (levels from the interview; values from `micro-motion`)
`--dur-fast`, `--dur-base`, `--dur-slow` · `--ease-out`, `--ease-in`, `--ease-in-out`.

### Data viz (derived by `color-system`, consumed by `data-viz`)
`--series-1…--series-6` (categorical, ≥3:1 vs background and adjacent series, ordered
so 1–2 work for color-blind readers) · `--chart-grid`, `--chart-label`.

## What to emit from the interview

A token block capturing the committed decisions, ready for the other skills to fill in
the generated values:

```css
:root {
  /* ---- PRIMITIVE (color-system generates the full ramp from the anchor hue) ---- */
  /* anchor hue from Q5; ramp via color-system/oklch-ramp */
  --brand-500: oklch(0.62 0.16 <H>);   /* ... 50–900 ramp ... */
  --neutral-500: oklch(0.62 0.012 <H>);/* neutrals tinted toward brand */
  --accent-500: oklch(0.65 0.18 <Haccent>);

  /* type faces from Q4 (web-typography builds the --step-* scale) */
  --font-display: "<Display>", serif;
  --font-body: "<Body>", system-ui, sans-serif;
  --font-mono: ui-monospace, monospace;

  /* shape & density from Q6 (spacing-system builds the --space-* scale) */
  --radius-control: <0–4|8–12|16+>px;
  --radius-card: <…>px;
  --radius-pill: 9999px;                /* tags/chips/avatars ONLY — never text CTAs */

  /* ---- SEMANTIC (what components use; theming remaps these per theme) ---- */
  --color-bg: var(--neutral-50);
  --color-surface-1: var(--neutral-100);
  --color-surface-2: var(--neutral-200);
  --color-text: var(--neutral-900);
  --color-text-muted: var(--neutral-600);
  --color-border: var(--neutral-200);
  --color-primary: var(--brand-600);
  --color-primary-hover: var(--brand-700);
  --color-primary-ink: var(--neutral-50);
  --color-accent: var(--accent-500);
  --color-accent-ink: var(--neutral-950);
  --color-focus: var(--brand-600);
}
```

Leave generated specifics (full ramps, type scale steps, spacing scale, motion values)
to the implementing skills — this block is the *contract*; they fill it in:
- **color-system** → full OKLCH ramp + verified-contrast semantic colors + `--series-*`.
- **web-typography** → fluid `--step-*` scale from the chosen faces, `--measure`, rhythm.
- **spacing-system** → the `--space-*` scale and section rhythm from the density choice.
- **theming** → light/dark/high-contrast remaps of the semantic tokens.
- **component-states / form-ux / empty-states** → implement using semantic tokens.
- **micro-motion** → `--dur-*`/`--ease-*` at the chosen motion level.
- **deslop-ui** → audits the built UI against this committed spec, not the average.

## Naming rules
- Semantic names describe **role**, not value: `--color-error`, never a hue name like
  "color-red".
- Primitives describe **value/scale position**: `--brand-600`, `--space-4`.
- Be consistent: `--{category}-{role|step}`. Don't mix conventions.
- One source of truth: the other skills *extend* this, never fork a parallel set.
- **Never rename these tokens per project.** The names are the inter-skill API; the
  *values* are where the project's taste lives.

## Why two tiers, not more
A common 2026 recommendation: stick to primitive + semantic when starting; only add
component tokens if a component genuinely needs to break from semantics. More tiers =
more indirection to maintain. Match the system's complexity to the project.
